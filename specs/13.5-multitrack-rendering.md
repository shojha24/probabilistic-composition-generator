# Spec 13.5 - Synchronized Multitrack Score Rendering

- **Status:** proposed implementation specification
- **Applies to:** `render.py`, `eda/validate_rendered_corpus.py`, tests,
  README documentation, and rendered-corpus tooling
- **Parents:** specs 09, 11, 12, and 13
- **Current tracks:** V0 chords/arpeggios, V1 bass, and V9 percussion

## 1. Decision

Directory rendering must emit one synchronized output set for every corpus
render. Given a mixed output path such as:

```text
gen/jazz_scores.txt
```

the renderer must write:

```text
gen/jazz_scores.txt
gen/jazz_scores_chords.txt
gen/jazz_scores_bass.txt
gen/jazz_scores_percussion.txt
gen/jazz_scores.txt.manifest.json
```

The mixed file remains the existing all-track score. The three role files
contain the same song blocks in the same order, with only their corresponding
JFugue voice:

| File | Voice | Content |
|---|---|---|
| `{name}.txt` | V0, V1, V9 | Mixed chord/arpeggio, bass, and percussion score |
| `{name}_chords.txt` | V0 | Chord pads or timed arpeggios |
| `{name}_bass.txt` | V1 | Bass track |
| `{name}_percussion.txt` | V9 | Audible or synchronized silent percussion |

The current output is one corpus-level file per role, not one filesystem file
per song. Each song remains a delimited block identified by
`START_SONG_N`/`END_SONG`. A later curation tool may copy those blocks into
per-song directories without changing this source export contract.

The renderer must render each source song once, retain the three generated
track strings, and fan them out to the four files. It must not rerender once
per output file or make additional random draws for track export.

## 2. Goals and non-goals

### 2.1 Goals

The implementation must:

1. preserve the current mixed score format and API behavior;
2. export V0, V1, and V9 as independently consumable JFugue score files;
3. keep song ordinals, block markers, source ordering, and manifest records
   identical across all four score files;
4. preserve exact track text when a role is extracted from the mixed score;
5. retain synchronized timelines, including silent V9 percussion;
6. make output paths, counts, hashes, and per-song pairing auditable;
7. write the complete output set atomically enough that consumers cannot
   mistake a partial set for a successful render; and
8. remain compatible with legacy mixed-only score artifacts.

### 2.2 Non-goals

This specification does not:

- change voicing, chord generation, arpeggio scheduling, bass generation, or
  percussion generation;
- add melody or a V2 export before melody rendering is implemented;
- create separate MIDI files for each track;
- change JFugue syntax, instrument programs, or voice assignments;
- infer a track by reparsing rendered audio; or
- replace the mixed score as the primary corpus/manifest pairing artifact.

V2 melody, when implemented by spec 14, must extend the same block and
manifest protocol rather than inventing an incompatible export format.

## 3. Current repository seam

`render.py` already produces the required logical parts in `_render_source()`:

```text
result["chord_track"]
result["bass_track"]
result["percussion_track"]
```

`render_directory()` currently writes:

```text
START_SONG_N
<chord_track>  <bass_track>  <percussion_track>
END_SONG
```

The implementation must preserve this assembly and additionally write the
three source track strings to their role files. The role strings are already
complete JFugue fragments, including tempo, voice, and instrument/program
prefixes. Do not remove those prefixes from sidecar files.

Current voice ownership remains:

- `ChordModule` owns V0 chord pads or instrument-aware arpeggios;
- `BassModule` owns V1;
- `PercussionModule` owns V9;
- `render.py` owns assembly, output ordering, and manifest pairing.

## 4. Output path contract

### 4.1 Derivation

The `--out` path remains the mixed score path. For an output with filename
`<stem><suffix>`, derive:

```python
mixed_path = output
chords_path = output.with_name(f"{output.stem}_chords{output.suffix}")
bass_path = output.with_name(f"{output.stem}_bass{output.suffix}")
percussion_path = output.with_name(
    f"{output.stem}_percussion{output.suffix}"
)
manifest_path = output.with_name(output.name + ".manifest.json")
```

The documented and tested suffix is `.txt`, producing the filenames shown in
section 1. The mixed path remains exactly the caller-provided `--out` value.
Role suffixes must be derived from the final mixed filename, not from the
input directory name or source song filenames.

Reject a derived path collision before rendering. In particular, no role file
may resolve to the mixed path or to another role file.

### 4.2 Multiple input directories

When multiple `--in-dir` values are supplied:

- process directories in command-line order;
- preserve the existing numeric filename ordering within each directory;
- assign one global output ordinal sequence across all directories; and
- write every ordinal to every output file.

The role files must not restart numbering at each input directory or genre.
The manifest remains the authority for mapping an output ordinal to
`source_dir`, `source_file`, and `source_id`.

## 5. Score block contract

### 5.1 Mixed file

The mixed file retains the current three-voice block format:

```text
START_SONG_0
T120 V0 I0 C4w+E4w+G4w  T120 V1 I32 C3w  T120 V9 Rs
END_SONG
```

The exact instrument programs and score tokens depend on the selected
voicer, bass instrument, render mode, percussion decision, and source
progression. The renderer must not normalize or rewrite those tokens merely
for export.

The mixed line must be assembled from the retained role strings in this order:

```text
<chord_track>  <bass_track>  <percussion_track>
```

This preserves the current V0, V1, V9 order and the current double-space
separator between role strings.

### 5.2 Role files

Each role file contains the same block markers and one role line per song:

```text
START_SONG_0
T120 V0 I0 C4w+E4w+G4w
END_SONG
```

The required role-to-voice mapping is:

```text
chords      -> V0
bass        -> V1
percussion  -> V9
```

The role line must be the exact retained role string from the render result.
It must not be rebuilt from the mixed line by deleting arbitrary tokens, and
it must not omit `T`, `V`, or `I` prefixes. This preserves absolute-time
tokens, arpeggio boundary markers, numeric durations, velocities, rests, and
instrument programs.

The chord file contains V0 pads in pad mode and V0 timed arpeggios in
arpeggio mode. It is not restricted to simultaneous chord tokens.

The percussion file must contain a V9 rest timeline when percussion is
omitted. Omission must never be represented by an empty block or by dropping
the song from the percussion file.

### 5.3 Ordinals and markers

For `N` rendered songs, every score file must contain exactly:

```text
START_SONG_0 ... START_SONG_{N-1}
```

with one matching `END_SONG` marker for each start marker. The ordered marker
sequence must be byte-identical across all four files. A source ID is not an
output ordinal: noncontiguous source filenames still receive contiguous
output ordinals according to the existing render order.

There must be exactly one score line between each pair of markers. Blank lines
are not permitted inside a score block. A file with a missing, duplicated,
nested, or reordered block is invalid even if its total song count matches.

## 6. In-memory rendering contract

### 6.1 Per-song result

Introduce an internal immutable result shape, or an equivalent typed mapping,
that retains the three role strings and their mixed assembly:

```python
@dataclass(frozen=True)
class RenderedSongTracks:
    ordinal: int
    chord_track: str
    bass_track: str
    percussion_track: str
    mixed_line: str
```

The names may differ, but the result must carry all five values. The mixed
line must be derived exactly once from the three role strings.

`_render_source()` may continue returning a mapping for compatibility, but it
must expose all three role strings to the directory writer. It must not invoke
any module a second time for a role file.

### 6.2 Public API compatibility

`render_song()` currently returns one mixed score string. Keep that behavior
unchanged for callers that only need an in-memory mixed score. Add a focused
track-aware helper if needed:

```python
render_song_tracks(
    progression: dict,
    seed: int | None = None,
    mode: str = "pads",
    *,
    percussion_percent: float | int | None = None,
) -> RenderedSongTracks
```

The helper must use the same module seeds and render decisions as
`render_song()`. `render_song()` may delegate to it and return
`result.mixed_line`, but no API path may render the parts independently.

`render_directory()` always emits the four-file output set. No opt-out flag is
required for the initial implementation; additional files are additive and
do not change the existing mixed score path.

## 7. Track synchronization invariants

### 7.1 Structural synchronization

For every output ordinal:

```text
mixed block ordinal
  == chords block ordinal
  == bass block ordinal
  == percussion block ordinal
  == manifest record ordinal
```

The mixed line's V0, V1, and V9 fragments must canonicalize exactly to the
corresponding role-file line. Canonicalization may normalize surrounding
whitespace for comparison, but it must not reorder tokens or change token
content.

The validator must check both directions:

1. every role file is represented in the mixed line; and
2. every mixed V0/V1/V9 role is represented in its role file.

### 7.2 Temporal synchronization

The existing semantic validator remains authoritative for chord content,
arpeggio provenance, bass correctness, percussion syntax, and no-chord
behavior. Multitrack validation adds:

- V0, V1, and V9 role files have the same source song count;
- each role preserves the source duration timeline;
- V9 silent songs contain synchronized rests rather than missing time;
- no role file introduces an onset or duration not present in its mixed role;
- timed V0 arpeggio markers are preserved in the chord file; and
- no-chord events remain rests in the chord and bass roles while percussion
  retains its synchronized V9 behavior.

The role files are symbolic exports. Matching token content is the primary
pairing invariant; audio-level synchronization remains the responsibility of
the existing MIDI renderer and its tests.

### 7.3 Track isolation

Writing sidecars must not change:

- selected voicer or source `VoicedChord` MIDI;
- V0 pad/arpeggio scheduling;
- V1 pitch, instrument, or pad-collapse result;
- V9 inclusion, kit, feel, or rest behavior;
- per-song mode allocation in mixed rendering; or
- any deterministic random stream.

For a fixed source directory and seed, rerunning the renderer must produce
byte-identical mixed and role files, manifest records, and output hashes.

## 8. Manifest and provenance

### 8.1 Existing fields

Retain all existing top-level and per-record manifest fields, including
command, seed, source directories, generator revision, render mode counts,
percussion settings, voicer counts, source hashes, and per-song render
decisions.

No top-level manifest version bump is required if consumers accept additive
fields, following the compatibility rule in specs 12 and 13. If the current
validator rejects additional schema fields, bump the version and make the
validator accept both the legacy mixed-only version and the new version.

### 8.2 Multitrack fields

Add a top-level `track_outputs` record:

```json
{
  "track_outputs": {
    "schema_version": 1,
    "song_count": 100,
    "voices": {
      "mixed": ["V0", "V1", "V9"],
      "chords": ["V0"],
      "bass": ["V1"],
      "percussion": ["V9"]
    },
    "paths": {
      "mixed": "/abs/gen/jazz_scores.txt",
      "chords": "/abs/gen/jazz_scores_chords.txt",
      "bass": "/abs/gen/jazz_scores_bass.txt",
      "percussion": "/abs/gen/jazz_scores_percussion.txt"
    },
    "sha256": {
      "mixed": "...",
      "chords": "...",
      "bass": "...",
      "percussion": "..."
    },
    "ordinals": [0, 1, 2]
  }
}
```

Paths must be resolved in the same manner as the existing manifest `output`
path. Hashes are SHA-256 hashes of the complete UTF-8 score files, including
the final newline.

Each record must retain the existing source pairing fields and add:

```json
{
  "ordinal": 0,
  "track_hashes": {
    "mixed": "...",
    "chords": "...",
    "bass": "...",
    "percussion": "..."
  }
}
```

Per-record hashes may be hashes of the canonical block (markers plus score
line) rather than the complete file. The field must be documented as a block
hash and must use the same canonicalization for all four roles.

The manifest is authoritative for:

- the output filenames;
- the expected role-to-voice mapping;
- total song count;
- output ordinal sequence;
- source-to-ordinal pairing; and
- complete-file and per-block hashes.

## 9. Atomic output installation

The current renderer already stages the mixed score and manifest through
temporary files. Extend the transaction to all four score files:

1. derive and validate all output paths before rendering;
2. render songs once and stage mixed/chords/bass/percussion text separately;
3. compute complete-file hashes;
4. stage the manifest with `track_outputs`;
5. install the complete set only after every staged file is ready; and
6. roll back the newly installed set if installation fails.

A failed render must not leave a new mixed file paired with old role files or
an old manifest. A pre-existing complete output set must remain intact if a
new set cannot be installed. Temporary files must be removed on success and
failure.

## 10. Validation tooling

### 10.1 New multitrack validator

Add a focused helper, for example:

```python
validate_multitrack_outputs(
    mixed_path: str | Path,
    chords_path: str | Path,
    bass_path: str | Path,
    percussion_path: str | Path,
    manifest_path: str | Path,
) -> dict
```

It must return a structured report consistent with the existing validator and
exit nonzero in CLI mode for hard failures.

Required hard-failure categories include:

```text
multitrack_missing_file
multitrack_manifest_mismatch
multitrack_song_count_mismatch
multitrack_ordinal_mismatch
multitrack_marker_mismatch
multitrack_voice_mismatch
multitrack_role_content_mismatch
multitrack_hash_mismatch
multitrack_timeline_mismatch
```

### 10.2 Backward compatibility

`validate_corpus()` must continue accepting legacy mixed-only outputs and
existing spec 12/13 manifests when no multitrack export is requested or
declared. When `track_outputs` is present, it must require and validate all
declared files.

The validator must not silently treat a missing role file as an empty track.
That is a hard pairing failure.

### 10.3 Canonical comparison algorithm

For each ordinal:

1. parse the mixed block and locate V0, V1, and V9;
2. parse the corresponding role blocks;
3. verify each role contains exactly its required voice and no other voice;
4. canonicalize only surrounding whitespace;
5. compare mixed role tokens with the role-file tokens;
6. compare marker and ordinal sequences across all files; and
7. run the existing semantic validation on the mixed score and source labels.

Do not compare tracks by source filename, lexical ordering, or line number
alone. Use output ordinal plus the manifest source mapping.

## 11. Determinism

Multitrack export must be a pure fan-out of an existing render result.
Writing a role file must not consume a random value or change a seed.

The following must be byte-identical across repeated runs with the same source,
seed, mode, percentage controls, and generator revision:

- mixed score;
- chords score;
- bass score;
- percussion score;
- manifest `track_outputs`;
- per-record track hashes; and
- existing per-song render decisions.

Changing only the output basename may change recorded output paths and the
command string, but must not change score content or per-record decisions.

## 12. Tests

Add focused tests in `tests/test_rendered_corpus.py` or a dedicated
`tests/test_multitrack_rendering.py`.

### 12.1 Output creation

1. A directory render creates all four score files and one manifest.
2. The default names are derived correctly from a `.txt` output path.
3. A non-sequential source filename order produces one identical ordinal
   sequence in all four files.
4. Multiple input directories produce one global, shared ordinal sequence.
5. `render_song()` retains its existing mixed-string return behavior.

### 12.2 Pairing and content

1. All four files contain the same `START_SONG_N`/`END_SONG` sequence.
2. Each mixed V0 fragment equals the corresponding chords block.
3. Each mixed V1 fragment equals the corresponding bass block.
4. Each mixed V9 fragment equals the corresponding percussion block.
5. Chord pads, timed arpeggios, `#ARPEVENT` markers, bass rests, and silent
   percussion are preserved exactly.
6. A zero-percent percussion render still writes a full synchronized V9
   percussion file.
7. Mixed pad, arpeggio, and mixed-mode renders all produce aligned sidecars.

### 12.3 Manifest and failure behavior

1. `track_outputs` paths, voices, song count, ordinals, and hashes match files.
2. Per-record block hashes match the corresponding blocks.
3. Missing, reordered, duplicated, or truncated role blocks fail validation.
4. Altering one role token causes a role-content or hash failure.
5. Legacy mixed-only output remains accepted when no multitrack declaration
   is present.
6. Repeated seeded renders produce identical output files and manifests.
7. A simulated output-install failure does not leave a mixed/sidecar mismatch.

### 12.4 Regression checks

The existing mixed score, manifest source pairing, pad/arpeggio semantics,
bass behavior, percussion behavior, no-chord handling, and Java MIDI
conversion input must remain valid. Sidecar creation must not alter any
existing score line or per-song manifest decision.

## 13. Implementation order

### Phase 1 - Track result and path derivation

- Add the typed/equivalent per-song track result.
- Preserve the current mixed assembly.
- Add deterministic role output path helpers.
- Add unit tests for naming and voice mapping.

### Phase 2 - Fan-out and manifest

- Stage four score files from one render pass.
- Add `track_outputs` and per-record track hashes.
- Extend atomic installation and cleanup.
- Update README usage and output documentation.

### Phase 3 - Validation

- Add block/voice/content/hash/timeline validation.
- Keep legacy mixed-only validation compatible.
- Add integration and failure-path tests.

## 14. Acceptance criteria

Spec 13.5 is complete only when:

1. Every directory render writes the mixed, chords, bass, percussion, and
   manifest files at deterministic derived paths.
2. The four score files contain identical ordered song markers and counts.
3. Each role file contains the exact corresponding role text from the mixed
   score, including rests, timing markers, programs, and arpeggio markers.
4. All output ordinals map one-to-one to manifest records and source hashes.
5. Sidecar creation does not change any existing mixed score text or render
   decision.
6. V0, V1, and V9 timelines remain synchronized, including silent percussion.
7. Complete-file and per-block hashes are recorded and validate successfully.
8. Partial or mismatched output sets fail clearly and cannot be mistaken for
   successful renders.
9. Existing mixed-only artifacts remain readable by the current validator.
10. Repeated seeded renders are byte-identical across all score files and
    manifest pairing metadata.
